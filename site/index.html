ZollyBot

Governed agent offices for your repositories. The agents run on your machine; you work them from any device.

Install on Linux

curl -fsSL https://zollybot.shifaul.dev/install.sh | sh

Installs two binaries into ~/.local/bin, verified against the release checksum:

  • zollybot — the desktop app (AppImage).
  • zollybot-cli — the terminal companion.

Then add the directory to your PATH if it is not there already, and run:

zollybot

First run

  1. Create or open a repository.
  2. Inside it, run zolly init to give that repository an office. The office is the .agents/ directory: rules, memory, queue and results, committed with the code.
  3. Start zollybot and pick the office. Every repository you open is its own office; nothing is shared between them.

Usage

Ask an office what it is doing

zollybot-cli offices
zollybot-cli queue shifaul-dev
zollybot-cli gates shifaul-dev

Every command takes --json for scripts. An office can be named by its path or by the frequency in its config (shifaul-dev, zylosync, …).

What the commands show

CommandAnswers
officesWhich repositories have an office, and how many tasks are queued, dispatched or blocked in each.
queue <office>Every queued brief with its status and gate.
gates <office>Results waiting for a human decision, and whether they were approved.

Gates and memory

Money, production, publishing and customers always stop for you. Code reaches the main branch only through the reviewer step. The app cannot skip either — the block lives in the backend, not in a prompt. Each office remembers its own decisions and lessons in .agents/memory/, written atomically and never by the UI directly.

How it fits together

  • An office is a repository, not a machine. Remove the app and the office still works from the terminal.
  • Files are the truth. Queue briefs, results, memory and the merge SHA live in git. There is no second database to trust.
  • Local first. Agents and files stay on the machine that owns the repository; remote devices are controls, not workers.
